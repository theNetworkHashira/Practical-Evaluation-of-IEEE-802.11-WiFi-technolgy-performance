# Output-folder guide

This document explains how to interpret the files generated by the Wi-Fi analysis programs. The output folder may contain results from three different workflows:

1. The packet-matrix workflow created by `matrix_maker-2.py`.
2. The interactive 3D visualization created by `plot3d_matrix-3.py`.
3. The standalone SoftAP-versus-AP comparison created by `wifi_mode_analysis_advanced.py`.

The files from these workflows should be interpreted together with the input-capture naming guide. The capture filenames identify the measurement location and whether the data came from a real access point or the Xiaomi SoftAP/mobile-hotspot setup.

## General interpretation rules

- A packet count measures observed frames, not necessarily unique devices or application-level messages.
- A frame subtype is a Wi-Fi/802.11 protocol category reported by the capture-processing pipeline.
- A higher count means that more matching frames were observed in the selected capture or time interval; it does not automatically mean better network performance.
- Comparisons are meaningful only when capture duration, capture position, channel or frequency, filtering, hardware, and environmental conditions are sufficiently comparable.
- Results describe what the capture adapter observed. They do not prove that every frame originated at the exact capture location.
- MAC addresses and other identifiers may be sensitive. Share output files responsibly, especially when they contain per-device information.

## Matrix-maker outputs

`matrix_maker-2.py` normally produces:

```text
packet_matrix_output.csv
```

### `packet_matrix_output.csv`

This is a wide-format packet-count matrix. Each row represents one frame subtype, grouped under a broad frame class.

Important columns include:

- `Main Type`: broad classification of the frame as `Management`, `Control`, `Data`, or `Other`.
- `Type/Subtype`: the more specific Wi-Fi frame subtype reported in the input CSV.
- Time-window columns such as `0.1s`, `0.2s`, and `0.3s`: the number of frames observed in each interval.

The configured `TARGET_MAX_TIME` determines the maximum processed duration. The configured `WINDOW_SIZE` determines the width of each time interval. For example, with `WINDOW_SIZE = 0.1`, each time column represents a 100 ms interval.

The script rebases timestamps so that the first usable packet occurs at approximately 0 seconds. Therefore, the time columns refer to elapsed time from the beginning of the processed capture rather than the original absolute timestamp.

### Reading a matrix row

Suppose a row contains:

```text
Main Type,Type/Subtype,0.1s,0.2s,0.3s
Control,Clear-to-send,4,1,0
```

This means that four Clear-to-send frames were observed in the first time window, one in the second, and none in the third. It does not indicate whether those frames were successfully used in a complete exchange.

The matrix is useful for identifying:

- Which frame subtypes are present.
- When bursts of control, management, or data traffic occur.
- Differences in traffic distribution across capture locations or modes.
- Candidate intervals for closer packet-level investigation.

The matrix does not preserve the complete order of individual packets. It is therefore not sufficient by itself to reconstruct a detailed frame exchange.

### Classification caveat

The broad class is assigned from text matching in the `Type/Subtype` value. Unusual or differently formatted subtype names may be placed in `Other`, or may not be classified exactly as expected. Always inspect the original subtype values when a result appears surprising.

## 3D-plot outputs

`plot3d_matrix-3.py` normally creates:

```text
<input-name>_3d_scatter.html
```

### Interactive HTML plot

Open the HTML file in a modern web browser. The plot can be rotated, zoomed, and inspected interactively.

The axes represent:

- X axis: the start of the time bin in seconds.
- Y axis: the frame subtype.
- Z axis: the packet count in that time bin.
- Marker size: packet count; larger markers represent more observed frames.
- Marker color: the color specified by the input `Hex` column.

Hovering over a point displays the count and, when available, the percentage and color information.

A high point or large marker indicates a concentration of a particular subtype during a particular time bin. Repeated points along the same subtype row indicate that the subtype appeared across multiple time intervals.

### Input-format limitation

The current 3D plotting script expects a long-format CSV containing at least:

```text
TimeBin,Type/Subtype,Count,Percentage,Hex
```

The matrix-maker output is wide-format and contains columns such as `0.1s`, `0.2s`, and `0.3s`. Consequently, `packet_matrix_output.csv` cannot be passed directly to the current 3D plotting script unless it is reshaped into the expected long format or the plotting script is modified.

The conceptual relationship is:

```text
wide packet matrix -> reshape into time-bin rows -> interactive 3D plot
```

## Standalone comparison outputs

`wifi_mode_analysis_advanced.py` creates an output directory containing CSV summaries, PNG figures, and `.meta.json` metadata files. The exact directory name is selected with `--outdir`.

The comparison uses two labels:

- `SoftAP`: the capture supplied through `--softap`.
- `AP`: the capture supplied through `--ap`.

### `frame_class_counts_by_mode.csv`

This file contains the number of observed frames in each broad class for each mode.

Columns:

- `Mode`: `SoftAP` or `AP`.
- `Class`: `Management`, `Control`, `Data`, or `Other`.
- `Count`: number of frames in that class.

Use this file to compare the overall traffic composition. A larger Management count may indicate more visible discovery, association, beacon, or action traffic, but it should not be interpreted as a direct measure of AP quality.

### `key_subtype_counts_by_mode.csv`

This file contains counts for selected subtypes, including examples such as beacons, probes, RTS/CTS frames, QoS Data, Block Ack frames, and Action frames.

Use it to examine which protocol mechanisms contribute to the broader class totals. A subtype absent from this file may still exist in the capture; this output only includes the predefined list of key subtypes.

### `control_to_data_ratio_by_mode.csv`

This file reports the number of Control frames per Data frame for each mode.

Interpretation:

- A higher value means more observed control traffic relative to data traffic.
- A lower value means data traffic made up a larger proportion of the observed frames.
- The ratio is sensitive to capture position, traffic load, retransmissions, protocol behavior, and filtering.

The ratio should be used as a comparative indicator rather than as a standalone performance metric. A high ratio is not automatically negative, because control exchanges can be normal and necessary for reliable communication.

### `per_mac_class_counts.csv`

This file breaks frame counts down by capture source address and broad frame class.

Columns:

- `Mode`: `SoftAP` or `AP`.
- `Source`: source identifier, commonly a MAC address.
- `Class`: broad frame class.
- `Count`: number of observed frames.

This output can help identify which observed transmitters contribute to Management, Control, Data, or Other traffic. Because source identifiers can be sensitive, this file should receive stricter access control than aggregate charts.

A source address with a high count is not necessarily the most active application device. It may represent an access point, a client, a broadcast-related transmitter, or a device whose traffic was more visible to the capture adapter.

### `pseudo_airtime_by_class.csv`

This file sums the `Length` field by mode and frame class. The result is labelled `PseudoAirtime` by the script, but it is not physical airtime.

Interpretation:

- Larger values indicate a larger total number of captured bytes in that class.
- The value can be useful for relative byte-volume comparisons.
- It does not account for PHY rate, modulation, coding, channel width, preamble, inter-frame spacing, retries, or actual on-air duration.

Treat this result as a byte-volume proxy, not as a measurement of channel occupancy or transmission time.

### `rts_cts_data_ack_sequences_by_mode.csv`

This file reports the number of adjacent timestamp-sorted rows matching the simplified pattern:

```text
Request-to-send -> Clear-to-send -> Data or QoS Data -> Acknowledgement or 802.11 Block Ack
```

A detected sequence is evidence that the corresponding subtype pattern appeared in that order in the capture. It does not prove that all four frames belonged to the same transmitter-receiver exchange.

The detector does not fully validate addresses, sequence numbers, duration values, retransmission state, or maximum inter-frame timing. Use packet-level inspection in Wireshark or a similar tool before making a strong protocol claim.

## PNG figures

The standalone analyzer exports the following main figures.

### `frame_class_mix.png`

Grouped bars compare Management, Control, Data, and Other frame counts between SoftAP and AP captures. Use this as the quickest overview of traffic composition.

### `key_subtypes_by_mode.png`

Grouped bars compare the selected protocol subtypes between modes. This helps explain which subtypes are responsible for visible differences in the frame-class chart.

### `control_to_data_ratio.png`

Bars show the Control-to-Data ratio for each mode. Interpret the result together with the underlying frame counts, because ratios can become misleading when the Data count is small.

### `cumulative_softap.png` and `cumulative_ap.png`

These line charts show cumulative frame counts over time, separated by broad frame class. Steeper sections indicate periods in which frames of that class accumulated more quickly.

The curves describe observed packet activity, not throughput. A steep Management curve, for example, indicates many observed Management frames, not necessarily successful client connections.

### `pseudo_airtime_by_class.png`

This chart visualizes the summed frame lengths by class and mode. Interpret it as relative captured byte volume, using the limitations described for `pseudo_airtime_by_class.csv`.

### `frame_subtype_timeline_softap.png` and `frame_subtype_timeline_ap.png`

These timelines place individual timestamped frames on rows grouped by subtype. The horizontal position shows time, while color and marker shape distinguish subtypes.

Small vertical offsets may be applied when several points share the same subtype row. These offsets improve readability and do not represent additional physical or protocol dimensions. The timeline is useful for finding bursts and apparent ordering, but it should not be treated as proof of frame relationships without further validation.

## Metadata files

Each PNG is accompanied by a file ending in:

```text
.png.meta.json
```

The metadata file records the chart caption and a short description. It can be used by scripts, reports, or future users to identify the intended meaning of an image without opening it.

## Recommended reading order

For a general comparison, inspect the outputs in this order:

1. `frame_class_counts_by_mode.csv` or `frame_class_mix.png` for the overall traffic composition.
2. `key_subtype_counts_by_mode.csv` or `key_subtypes_by_mode.png` to identify the subtypes behind the differences.
3. `control_to_data_ratio_by_mode.csv` or `control_to_data_ratio.png` for relative control traffic.
4. The cumulative timelines to examine when traffic accumulated.
5. The subtype timelines to investigate individual event timing.
6. `per_mac_class_counts.csv` for source-level analysis, with appropriate privacy controls.
7. The sequence and pseudo-airtime outputs for cautious, supporting analysis.

## Responsible interpretation

The generated outputs are observational summaries of packet captures. They are not, by themselves, proof of network performance, user behavior, successful protocol exchanges, or causal relationships.

When presenting results, report the capture conditions, input filenames, capture duration, location, mode, filtering settings, and relevant script parameters. Avoid publishing raw MAC addresses or other potentially identifying fields unless disclosure is justified, authorised, and consistent with applicable privacy and institutional requirements.
